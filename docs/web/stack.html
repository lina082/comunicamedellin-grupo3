Vista general

Las cuatro capas

El color marca la decisión CAP de cada pieza: teal donde priorizamos disponibilidad, ámbar donde priorizamos que el dato no se pierda.

Apache Kafka
Transporte · fan-out

Log inmutable y particionado. Recibe la alerta una sola vez y la reparte en tres particiones, una por zona, para que tres workers entreguen en paralelo sin pisarse.

Modo KRaft: el consenso vive dentro del broker, sin Zookeeper.

apache/kafka:3.9.1 KRaft 3 particiones Sec. 4.2
Apache Cassandra
Almacenamiento · 3 nodos

El corazón del reto. Guarda la presencia como clave-valor y el historial como wide-column. Es la única pieza que permite elegir el nivel de consistencia por consulta: ONE, QUORUM o ALL.

Factor de replicación 3 — cada dato vive en los tres nodos, que es lo que hace observable la diferencia entre niveles.

cassandra:4.1 RF=3 heap 512 M por nodo Sec. 1.3 · 3.3
ClickHouse
Analítica · OLAP

Motor columnar para las agregaciones que Cassandra no resuelve bien: cuántos usuarios en línea por zona, efectividad del fan-out, percentiles de latencia.

Consume del tópico de Kafka con su Kafka Engine nativo — sin escribir un consumer.

clickhouse-server:24.3-alpine MergeTree Sec. 2.2 · 2.4
FastAPI + HTML
Aplicación · demo visual

API con WebSocket que lee el mismo usuario desde dos nodos a la vez y transmite la divergencia en vivo. El frontend es un solo archivo HTML: sin Node, sin npm, sin build.

Recorrido de un dato

Qué pasa cuando la alcaldía publica una alerta

01
POST /alerta → FastAPI
Una sola escritura entra al sistema. Aquí todavía no hay nada distribuido.
02
FastAPI → Kafka · partición por zona
La alerta se publica tres veces, una por zona. Norte va a la partición 0, centro a la 1, sur a la 2. Fijamos la partición explícitamente porque el hash de Kafka hacía colisionar norte y sur.
03
3 workers consumen en paralelo
Cada worker toma su partición y escribe el historial de sus usuarios. Aquí es donde una escritura se convierte en cien mil.
04
Workers → Cassandra · nivel QUORUM
El historial va con QUORUM: la alerta es seguridad pública y no se puede perder. Aceptamos pagar latencia aquí porque se publica poco.
05
Dispositivos → Cassandra · nivel ONE
En paralelo, los usuarios reportan presencia constantemente. Eso va con ONE: barato, y que llegue tarde no le cuesta nada al negocio.
06
Kafka → ClickHouse · vía Kafka Engine
La ruta analítica consume el mismo log y agrega por zona y por hora. Es una arquitectura Lambda: ruta rápida y ruta analítica alimentadas por el mismo flujo.

Requisito de equipo

Con 8 GB de RAM corre sin problema. Los heaps de Java están recortados a propósito — 512 MB por nodo de Cassandra contra los 4 GB que trae por defecto. Es una demo, no producción.

Ojo con esto

La API corre en 8765, no en 8080. Al probar encontramos que 8080 lo tenía tomado un Jenkins y 8090 otra aplicación. Si les falla, revisen que el puerto esté libre.

Kafka expone dos listeners: kafka:9092 para que ClickHouse lo alcance dentro de Docker, y localhost:29092 para los scripts que corren en su máquina.

Decisiones

Lo que descartamos

Saber defender esto importa tanto como el stack elegido — es donde el jurado prueba si entendimos.

CockroachDB

ES CP, NECESITAMOS AP

Usa consenso Raft: los tres nodos siempre coinciden. Eso lo hace ideal para TuBoleta, pero aquí el reto exige mostrar divergencia entre nodos — y en Cockroach esa divergencia no existe. Su licencia BSL tampoco es open source.

Redis

NO ES LA PIEZA QUE PIDE EL MÓDULO

El módulo lo cataloga como feature store para ML Sec. 4.4, no como base de datos distribuida. Y no permite elegir nivel de consistencia por consulta, que es justo lo que el reto pide demostrar.

PostgreSQL solo

ES CLIENTE-SERVIDOR

Aunque esté en la nube, sigue siendo la arquitectura de la Sec. 3.2: el servidor es el cuello de botella. El enunciado advierte explícitamente contra confundir “en la nube” con “distribuido”.

MongoDB

ES CP POR DISEÑO

El módulo lo clasifica como CP Sec. 1.2. Prioriza consistencia sobre disponibilidad, que es lo contrario de lo que este caso necesita.

Extra

El perfil Zookeeper

Kafka corre en modo KRaft, que es lo moderno. Pero dejamos un segundo perfil con Zookeeper por una razón puntual: poder ver cómo funciona un servicio de coordinación distribuida.

Está en la Sección 1.3 del módulo, junto a etcd, Raft y Paxos. Con make zk-shell pueden entrar y mirar:

ls /brokers/ids      # los brokers registrados
get /controller      # quién ganó la elección de líder
ls /brokers/topics   # metadata de tópicos
Dato para la exposición

Kafka 3.5 marcó Zookeeper como obsoleto y Kafka 4.0 lo eliminó del todo. Poder contar esa migración — de coordinación externa a consenso embebido vía Raft — es algo que ningún otro equipo va a mencionar.
